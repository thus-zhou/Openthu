# 完整升级批次与版本交付

## 默认工作单位

一个升级批次对应一个完整、可验收的产品改进目标，可以包含多个模块。默认采用 **一个版本计划、一个集成分支、一个版本 PR、一次整体审查、一次正式发布**。模块继续拆小、及时提交和推送，避免累积未保存工作；模块完成通过 commit 和进度清单记录，不逐模块开 PR、交审或结束任务。

## 1. 先形成可执行的完整计划

Hermes 先盘点代码、已有 PR、已知缺陷及用户目标，将 `plans/UPGRADE_TEMPLATE.md` 复制为该批次的计划，填写目标版本、用户可见结果、范围、模块依赖、验收标准、兼容和回滚办法。选取能组成完整交付的改进，不以代码量或模块数作为升级成果。

已有明确版本升级授权时，Hermes 可在该范围内自行落实计划并连续开发，不逐模块等待批准。总体目标未给出、范围变化会影响已有功能或涉及新的具体校园业务时，先明确缺失的决定；期间继续独立且已授权的工作。不把路线图所有愿望无条件纳入一个版本。

## 2. 一条集成分支持续完成

使用 `hermes/release-vX.Y.Z` 或明确的批次分支；原有任务分支可继续作为该批次集成分支，避免搬动、丢弃已完成代码。每个模块完成后提交、推送、更新版本计划，随后继续下一个模块。子任务可以有 Issue，但不要求每个子任务有 PR。

默认整体完成后创建一个版本 PR；需要提前展示进度时，可从开始就创建同一个 Draft PR，后续持续更新。不得为同一版本重复开多个模块 PR。独立紧急修复或确需隔离的贡献可以另开 PR，必须在版本计划中说明原因。

## 3. Hermes 负责做到候选版本

负责版本内各模块实现、相互集成、必要测试与全量回归、安装与升级路径、兼容检查、隐私检查、能力矩阵、变更记录、回滚方案，以及候选包和发布说明。同步版本号但保留未发布状态；候选包不等于正式发行。

遇到局部阻塞，保留现场并继续不依赖它的模块。确实需要 Codex 介入时，在原版本 PR 记录具体问题和交接范围；人工接力解决后继续同一版本。需要本机实测的部分建立明确请求，不能以云端模拟结果代替；没有具体业务授权时，真实写入保持待验，不为验收而创建真实预约。

局部接力且双方仍有工作时，Codex 使用辅助分支或提供明确补丁，由集成分支负责者接回；避免两方同时推送同一分支。辅助修复仍归入原版本 PR，不因此拆出多个版本交付。

## 4. 整体提交审查的门槛

- 计划内模块全部落实并完成集成；范围调整和未完成项有明确解释。不能静默删减验收项后声称完整完成。
- 相关测试、全量离线回归、MCP 检查、隐私检查通过；Windows/Linux 结果分别记录。
- 候选包可以恢复安装；依赖、许可证、配置模板、版本号、文档和能力状态一致。
- 提供整体变更说明、验证摘要、已知限制、回滚步骤及需要本机核对的事项。
- 把同一个版本 PR 标为 Ready for review，明确“完整版本候选已完成，交 Codex 整体审查”，再通知使用者。

## 5. Codex 审查后正式发布

Codex 独立检查整个候选的实现、风险、验收证据、公开内容与打包。需要修改时在同一 PR 交回 Hermes，修复后重验。完成审查和必要本机验证后，由 Codex 合并、创建版本标签、发布 Release 并核对公开下载。

一个小模块通过、PR 已建立或 CI 变绿，都不自动触发正式 Release。用户可以通过版本 PR 链接请求审查或指定范围的接手。

## 会话结束与继续

本规则改变任务和交付粒度，不改变 Hermes 的会话运行上限。会话因上下文、额度、时限或外部条件结束时，记录已完成模块、未完成工作、分支、提交和下一步。使用者让它继续后，从该断点推进，不重新拆出小 PR。仍采用人工触发接力，不增加后台 AI 调度。
