# 5.3 网络学堂作业上传与正式提交

版本目标：Openthu v0.2.0｜批次：5｜状态：待实施方案

【执行方案本体】

## 一、目标与开工条件

在可靠来源契约成立后新增受保护的作业正式提交适配，同时保持旧 prepare_submission 仅作本地校验，让文件上传、草稿和最终提交的副作用都能够被精确授权和核对。

必须先取得第4批全部模块（4.1、4.2、4.3、4.4、4.5）验收并回接的集成提交。本批同批模块可并行，仍须遵守独占路径及冻结接口；前后批不得重叠开工。

先读取总控、本模块和第一批冻结结果，核对实际提交与上批验收，不从聊天里的旧完成汇报推断当前状态。工作区有未提交内容时先辨明负责者和来源，保留改动，不执行强制重置、清空目录或覆盖式拉取。发现基线不同先登记差异，解决后再实施，不能边写边猜依赖版本。

## 二、修改范围与并行纪律

新增 src/thu_assistant/submissions/ 与提交测试；保留 learn_assistant/core.py 的准备工具语义，公共注册由 6.1 完成。

本模块对列明路径负责，新增目录也要登记。你并非仓库中的唯一执行者，不撤销他人提交；同批只读公共契约，在独立辅助分支开发，不同时向集成分支推送。同批缺少的实际组件可以用冻结协议的显式夹具开发，夹具不得进入生产默认路径；回接后再核对真实接线。需要修改他人文件时先登记交叉请求，由集成人处理，不能扩大自己的修改范围。

## 三、实施顺序

按下列步骤小步推进，每一步先确定输入、输出与可能副作用，再实现最小可核对改动。保留原有兼容测试，新增用例围绕行为、故障和边界，不写只复制实现细节的空断言。发现失败先定位归属并保留复现；只暂停受影响路径，独立且已授权的工作可继续。修复后重跑受影响检查，不重复运行已经通过且未被新改动影响的整套测试。

1. 首先核对来源启动结论，确认上传、草稿、最终提交及提交记录查询的真实契约。没有这些依据时只建立适配边界和明确未支持结果，不能从旧提交摘要推导学校接口，也不能把模拟上传结果用在生产环境。

2. 读取作业当前说明、截止与补交条件、文件限制和已有提交状态，复用旧本地校验形成候选文件集。准备阶段只检查和计算哈希，不上传、不保存远端草稿；已有作业提交时必须明确本次是否涉及替换，不能默认为覆盖。

3. 冻结文件清单和业务摘要，包含作业、课程、源记录、文件内容哈希、大小、类型及选定说明。预览后再次读取文件并核对哈希，文件在本地被修改、移动或替换时使旧计划失效，不能继续提交新内容而保留旧摘要。

4. 将上传也放入统一事务请求序列，在派发前保存意图并取得该笔授权。多文件按明确顺序处理，记录每个已发出步骤与远端临时引用；若上传产生草稿或占用状态，其副作用必须出现在预览和日志中，不能宣称只有最终按钮才是写入。

5. 在最终提交前重新核对作业状态、限制、截止与可替换条件。平台要求新的确认、声明或官方验证时返回需要处理，授权范围改变必须重新准备；超过期限或已有他端提交的情况停止，而不是反复尝试覆盖。

6. 最终提交后查询本人提交记录，核对作业、版本、文件清单和平台提供的时间或回执。只有平台确实提供文件哈希或可验证内容时才能声称内容完全一致，缺乏此证据应保留可证明的字段及验证限制。

7. 对上传响应丢失、仅保存草稿、部分文件成功和最终提交未知分别设计恢复路径。重复执行只核对已有状态，不自动重新上传；清理临时附件或撤回属于独立动作，平台不支持时明确保留残留状态供使用者处理。

8. 保持旧工具输出兼容，新增办理挂载统一准备与执行入口，不能让旧 prepare_submission 因升级突然变成会上传的命令。对每阶段的副作用、取消和失败进行合成测试，公开文档准确说明已实现与未启用范围。

## 四、数据与接口约定

提交计划使用独立操作名并包含作业编号、课程来源、文件清单摘要、替换策略及必要的平台版本。结果区分上传中、草稿已保存、提交待核对、已核对及未知；旧工具的 submit_supported 语义不能被无依据改为真。

## 五、异常、退化与兼容

附件变化、截止变化、已有提交冲突、上传未知、提交未知与平台拒绝分别处理。任何超时都不等同于尚未提交。未取得正式提交来源契约时保持关闭，不能以手动拼接请求或自动点击通用按钮替代适配。

## 六、必须覆盖的验收用例

用例都使用合成账号、事件、文件和假校园传输；默认拦截外发请求，记录读取与写入次数。本地真实浏览器仅访问合成页面，工程验证不需要真实占座、付款或交作业。测试编码器与生产密钥后端必须可辨别，不能以开启假加密换取通过。跳过检查写明平台原因，未执行、模拟通过和真实业务证据分别记录。

- 运行旧 prepare_submission 时，合成远端上传与提交计数必须为零。
- 预览后修改文件内容，即使文件名不变也必须拒绝执行旧计划。
- 多文件第二项上传失败时，应保留第一项副作用和后续恢复状态。
- 上传响应丢失后再次执行，不能未经核对就重新上传同一文件。
- 草稿已保存但没有最终提交回执时，不得输出已交作业。
- 已有提交且缺少替换授权时，必须拒绝覆盖。
- 平台只提供文件名时，结果不得伪造已验证哈希一致。
- 清理草稿和代码回退均不能自动撤回或重交正式作业。

## 七、回退与恢复

先关闭新正式提交入口，保持旧查询、本地准备和新事务结果核对。保留已经上传的临时引用及说明，不主动删除远端附件；对使用者已完成提交的作业不进行任何反向操作。

## 八、交付、回接与结束条件

交付正式提交适配、各阶段状态机、文件变更保护和未知结果恢复用例。没有可靠接口依据时必须登记阻塞，不能为了满足版本功能数量把准备工具改名成提交工具。

交付安全的模块结果说明与机器可读摘要，包含模块编号、基线、最终提交、负责路径、执行检查、结果和剩余阻塞。原始异常、认证响应、主机信息和用户目录不提交；公开摘要只保留错误类别及合成复现。提交前检查差异与隐私，模块代码及时提交推送，进度更新到原版本计划，不为本模块新建交付 PR。

单模块通过不等于批次通过。集成人按顺序回接同批成果，核对无冲突、无遗漏并完成契约联调后，形成唯一批次提交，才允许下一批开工。常规先执行差异检查和本模块必要用例；批次回接再运行开发检查与全量离线回归，命令沿用 python scripts/dev.py check 和 python scripts/dev.py test。若命令因本批修改变化，先核对兼容说明，不自行换成不覆盖相同行为的简化检查。

遇到缺来源、缺授权或不可恢复冲突时保留明确阻塞，禁止用伪造接口、真实个人数据或弱化保护消除问题。会话到达运行限制前保存已完成步骤、提交、下一条动作和待核对事项；恢复会话后沿用原模块与版本分支。需要 Codex 接手时交出具体范围，整套版本仍由原总任务跟踪。
