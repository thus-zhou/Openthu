# 1.1 版本基线、架构契约与调度冻结

版本目标：Openthu v0.2.0｜批次：1｜状态：待实施方案

【执行方案本体】

## 一、目标与开工条件

建立整套升级的唯一实施基准，把二十四个模块的边界、依赖、数据结构和完成标准固定下来，防止不同执行者各自设计接口，或者把尚未取得依据的新能力当成已经完成。

无前批，首先执行基线核对。本批为单模块串行关口，不与前后批重叠执行。

先读取总控和本模块，第一批冻结结果由本模块生成；核对实际提交与已存在的基线验收，不从聊天里的旧完成汇报推断当前状态。工作区有未提交内容时先辨明负责者和来源，保留改动，不执行强制重置、清空目录或覆盖式拉取。发现基线不同先登记差异，解决后再实施，不能边写边猜依赖版本。

## 二、修改范围与并行纪律

plans/v0.2.0、contracts/v0.2、版本总清单；本模块不修改生产业务实现。

本模块对列明路径负责，新增目录也要登记。你并非仓库中的唯一执行者，不撤销他人提交；同批只读公共契约，在独立辅助分支开发，不同时向集成分支推送。同批缺少的实际组件可以用冻结协议的显式夹具开发，夹具不得进入生产默认路径；回接后再核对真实接线。需要修改他人文件时先登记交叉请求，由集成人处理，不能扩大自己的修改范围。

## 三、实施顺序

按下列步骤小步推进，每一步先确定输入、输出与可能副作用，再实现最小可核对改动。保留原有兼容测试，新增用例围绕行为、故障和边界，不写只复制实现细节的空断言。发现失败先定位归属并保留复现；只暂停受影响路径，独立且已授权的工作可继续。修复后重跑受影响检查，不重复运行已经通过且未被新改动影响的整套测试。

1. 核对主分支与现有草稿的提交，记录主分支代码、工具目录、测试基线和工作区状态。PR #2 的两个已有提交仅登记为待收编成果，先验证差异再使用；不得因旧报告说完成就跳过审查，也不得覆盖云端尚未提交的工作。

2. 建立一个版本集成分支，原则上延续 PR #2 的分支和草稿，另建分支时必须说明继承关系。为每个模块记录负责者、独占修改路径、输入契约版本、预期输出和回接顺序；模块开发分支只服务同一个版本交付。

3. 冻结统一结果信封，保留现有状态、来源、检查时间、完整性、警告和验证级别。新增实现状态、运行可用性和证据等级采用可选字段，分别表达代码存在、环境可运行和来源已核对，不让一个成功布尔值代替三种含义。

4. 冻结业务门面，约定只读查询、具体计划准备、计划执行、结果核对、健康查询和主动取消的调用形式。冻结本地看板读取接口的路径、参数及分页结构，使后面的客户端模块可以针对契约夹具并行开发，不等待共享文件被反复改写。

5. 冻结持久化格式、账号域、服务域、存储用途和版本字段，约定凭据、会话、事务、索引、图片、事件游标分别使用不同用途标识。定义同一资源在缓存、待办和日历中的稳定标识，不通过姓名、标题或数组位置猜测身份。

6. 按总目录建立批次状态机和交付清单。前批全部模块通过验收并回接同一个集成提交后，才开启下一批；同批模块不得暗中依赖彼此尚未提交的实现，需要交叉修改时先登记冲突，由集成人统一处理。

7. 把范围分为必须完成的产品底座与受来源契约约束的新适配。来源不足的学业、提交、续借和图片传输能力必须登记阻塞条件，不能用模拟通过冒充平台支持；若影响承诺范围，停在候选阶段，由使用者决定范围调整。

8. 建立总体验收映射，把每个功能对应到代码、契约、用例、安装资产和文档。先检查计划是否存在遗漏、循环依赖、重复负责路径或未指定的公共文件，再签出首个基线标签或提交，给后续模块提供准确引用。

## 四、数据与接口约定

契约文件至少包含结果信封、错误分类、存储头、来源证据、媒体引用、日程事件、业务门面和本地读取接口八类。枚举只描述项目内部语义，不能推断学校真实字段。每个契约要有版本、必填字段、未知值表示、兼容样例和拒绝样例；公共工具仍以现有二十九个入口为兼容基线。

## 五、异常、退化与兼容

基线发生外部更新时先比较差异，不静默重建计划。发现现有文档与代码冲突，以当前注册实现及可追溯证据为依据登记修订。契约冻结后新增字段必须经过变更记录、影响模块清单和适配方案，未处理影响前不得宣布批次完成。

## 六、必须覆盖的验收用例

用例都使用合成账号、事件、文件和假校园传输；默认拦截外发请求，记录读取与写入次数。本地真实浏览器仅访问合成页面，工程验证不需要真实占座、付款或交作业。测试编码器与生产密钥后端必须可辨别，不能以开启假加密换取通过。跳过检查写明平台原因，未执行、模拟通过和真实业务证据分别记录。

- 核对旧客户端请求与结果结构，新增字段缺省时必须保持原有调用可用。
- 遍历全部模块依赖，确认无环且每条依赖只指向前批已完成产物。
- 比较同批独占路径，出现同一可写文件时必须重新分配而非允许碰运气合并。
- 用同名不同编号的课程、资源和订单验证稳定标识不能被标题替代。
- 把来源失败、真实空列表和部分读取作为三组夹具，确认信封可区分。
- 为未知来源契约建立阻塞样例，确认它不会被计为已实现业务。
- 检查版本草稿、分支和总清单的一致性，确认模块完成不会新建发行。
- 检查计划包不包含原始账号数据、私人路径、认证链接或机器标识。

## 七、回退与恢复

本模块仅新增计划和契约，回退时保留已经存在的代码分支及 PR #2 成果。废止的契约标记为未启用，不删除后续模块已经引用的版本；若尚未开工，可通过单独修订提交统一替换。

## 八、交付、回接与结束条件

交付冻结基线、模块负责表、契约目录、兼容样例及批次门禁记录。必须能从任一模块反查输入与验收，不存在共享文件的无人负责区域。后续执行者只需读取总控、本模块输出和自己的方案即可开始工作。

交付安全的模块结果说明与机器可读摘要，包含模块编号、基线、最终提交、负责路径、执行检查、结果和剩余阻塞。原始异常、认证响应、主机信息和用户目录不提交；公开摘要只保留错误类别及合成复现。提交前检查差异与隐私，模块代码及时提交推送，进度更新到原版本计划，不为本模块新建交付 PR。

单模块通过不等于批次通过。集成人按顺序回接同批成果，核对无冲突、无遗漏并完成契约联调后，形成唯一批次提交，才允许下一批开工。常规先执行差异检查和本模块必要用例；批次回接再运行开发检查与全量离线回归，命令沿用 python scripts/dev.py check 和 python scripts/dev.py test。若命令因本批修改变化，先核对兼容说明，不自行换成不覆盖相同行为的简化检查。

遇到缺来源、缺授权或不可恢复冲突时保留明确阻塞，禁止用伪造接口、真实个人数据或弱化保护消除问题。会话到达运行限制前保存已完成步骤、提交、下一条动作和待核对事项；恢复会话后沿用原模块与版本分支。需要 Codex 接手时交出具体范围，整套版本仍由原总任务跟踪。
