# 2.1 收编安装诊断与统一配置路径

版本目标：Openthu v0.2.0｜批次：2｜状态：待实施方案

【执行方案本体】

## 一、目标与开工条件

在保留已有贡献的基础上，把安装检查、路径解析和配置优先级变成其他模块可以依赖的稳定底座，让源码运行、虚拟环境安装和后续完整发行使用同一种位置解析规则。

必须先取得第1批全部模块（1.1）验收并回接的集成提交。本批同批模块可并行，仍须遵守独占路径及冻结接口；前后批不得重叠开工。

先读取总控、本模块和第一批冻结结果，核对实际提交与上批验收，不从聊天里的旧完成汇报推断当前状态。工作区有未提交内容时先辨明负责者和来源，保留改动，不执行强制重置、清空目录或覆盖式拉取。发现基线不同先登记差异，解决后再实施，不能边写边猜依赖版本。

## 二、修改范围与并行纪律

scripts/dev_diagnostics.py、scripts/dev.py、新增 src/thu_assistant/configuration.py、paths.py 与对应配置测试；包元数据由 6.3 负责。

本模块对列明路径负责，新增目录也要登记。你并非仓库中的唯一执行者，不撤销他人提交；同批只读公共契约，在独立辅助分支开发，不同时向集成分支推送。同批缺少的实际组件可以用冻结协议的显式夹具开发，夹具不得进入生产默认路径；回接后再核对真实接线。需要修改他人文件时先登记交叉请求，由集成人处理，不能扩大自己的修改范围。

## 三、实施顺序

按下列步骤小步推进，每一步先确定输入、输出与可能副作用，再实现最小可核对改动。保留原有兼容测试，新增用例围绕行为、故障和边界，不写只复制实现细节的空断言。发现失败先定位归属并保留复现；只暂停受影响路径，独立且已授权的工作可继续。修复后重跑受影响检查，不重复运行已经通过且未被新改动影响的整套测试。

1. 先逐项审查 PR #2 中的诊断实现与六组测试，比较其依赖判断、进程调用和公开输出。保留有效代码及原作者提交依据；存在缺陷时在版本集成分支修正，不额外为安装模块创建新的交付 PR。

2. 明确配置来源顺序，采用命令行明确参数、项目专用环境变量、本机配置文件和安全默认值。不同来源不能隐式合并秘密；未知键、重复键、非法类型与不可读文件必须报出稳定错误，报告只给相对配置项名称。

3. 建立统一路径解析器，分别定位程序资源、用户私有状态、下载、临时文件和日志。资源目录只读，状态默认在代码库之外；用户自选位置要展开和规范化，拒绝覆盖程序资源、密钥目录及其他受保护目标。

4. 把仓库级运行资源和将来的包内资源抽象成同一资源描述。暂时保留源码布局兼容，提供可查询的完整资源清单，不把开发者电脑上的绝对目录写成默认值；缺少辅助代码时返回缺资源，而非搜索整台电脑寻找旧安装。

5. 改善 doctor 的分项检查，区分开发依赖、只读功能、浏览器、生产认证和打包资源。虚拟环境缺失可以提示而不错误阻断合法安装；版本范围必须和项目声明一致，不把某次验证版本误当成所有平台唯一可用版本。

6. 修正 Windows 下脚本与可执行文件的发现和调用，特别处理 npm.cmd，避免把任意修复提示交给 shell 自动执行。外部命令限定参数、超时和输出长度；版本字符串验证格式，错误输出先清洗后进入诊断结果。

7. 保持 check、smoke、test 和 setup-node 的原有退出语义，新诊断报告区分错误、警告和不适用。敏感服务未配置时应说明对应能力不可用，不能把无学校凭据视为开发环境安装失败，也不能为了让诊断变绿触发登录。

8. 提供配置样例和纯合成诊断夹具，给后续安全存储、会话、看板和发行模块提供只读配置接口。输出每项诊断的修复建议，但由使用者或执行模型在授权范围内落实，不自动下载未知脚本或修改全局用户配置。

## 四、数据与接口约定

配置对象至少区分资源、存储、运行时、网络和界面五个分组，秘密值不属于可公开序列化字段。诊断条目固定为标识、状态、可用版本、简短原因、修复命令和适用能力；状态采用通过、警告、失败、不适用，聚合退出码必须由错误级条目决定。

## 五、异常、退化与兼容

环境探测失败不能伪装为依赖不存在。路径无权访问、命令超时和版本不支持分别报告；显式配置无效时停止使用该配置，不悄悄切回另一账号或旧目录。迁移只给出预览和目标，不在本模块搬移任何真实会话。

## 六、必须覆盖的验收用例

用例都使用合成账号、事件、文件和假校园传输；默认拦截外发请求，记录读取与写入次数。本地真实浏览器仅访问合成页面，工程验证不需要真实占座、付款或交作业。测试编码器与生产密钥后端必须可辨别，不能以开启假加密换取通过。跳过检查写明平台原因，未执行、模拟通过和真实业务证据分别记录。

- 正常源码环境应通过诊断且不发出学校网络请求。
- 分别移除 Python 包、Node 与 npm，确认原因和修复建议对应缺失项。
- 使用 Windows 脚本路径和含空格目录，确认参数不会被拆分执行。
- 让命令输出私人路径、令牌样式和异常长文本，确认公开报告不会泄露原文。
- 构造损坏配置、未知字段和相对状态目录，确认失败路径可解释且不改写原文件。
- 在没有浏览器或没有密钥的环境中，分别验证开发能力和生产能力的判定。
- 模拟包内资源和源码资源，确认两者返回同样的逻辑资源标识。
- 检查旧命令退出码与现有自动检查调用方式保持兼容。

## 七、回退与恢复

回退时恢复旧命令入口和配置解释器，新增配置文件保留为未启用，不删除使用者已有设置。路径迁移尚未执行，其他模块不得将本模块回退解释为允许覆盖状态目录。

## 八、交付、回接与结束条件

交付诊断收编记录、配置模型、路径解析器和行为矩阵。后续模块不再自行拼接用户目录或重复读取环境变量；出现新的配置需求时通过冻结契约登记，禁止私增不受检的认证参数。

交付安全的模块结果说明与机器可读摘要，包含模块编号、基线、最终提交、负责路径、执行检查、结果和剩余阻塞。原始异常、认证响应、主机信息和用户目录不提交；公开摘要只保留错误类别及合成复现。提交前检查差异与隐私，模块代码及时提交推送，进度更新到原版本计划，不为本模块新建交付 PR。

单模块通过不等于批次通过。集成人按顺序回接同批成果，核对无冲突、无遗漏并完成契约联调后，形成唯一批次提交，才允许下一批开工。常规先执行差异检查和本模块必要用例；批次回接再运行开发检查与全量离线回归，命令沿用 python scripts/dev.py check 和 python scripts/dev.py test。若命令因本批修改变化，先核对兼容说明，不自行换成不覆盖相同行为的简化检查。

遇到缺来源、缺授权或不可恢复冲突时保留明确阻塞，禁止用伪造接口、真实个人数据或弱化保护消除问题。会话到达运行限制前保存已完成步骤、提交、下一条动作和待核对事项；恢复会话后沿用原模块与版本分支。需要 Codex 接手时交出具体范围，整套版本仍由原总任务跟踪。
