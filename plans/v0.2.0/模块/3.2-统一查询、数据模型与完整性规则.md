# 3.2 统一查询、数据模型与完整性规则

版本目标：Openthu v0.2.0｜批次：3｜状态：待实施方案

【执行方案本体】

## 一、目标与开工条件

把不同校园来源返回的数据变成一致而可追溯的业务结果，为学业、资料、待办和看板提供稳定语义，重点避免缺页、缓存和失败造成错误的空结果或错误合并。

必须先取得第2批全部模块（2.1、2.2、2.3）验收并回接的集成提交。本批同批模块可并行，仍须遵守独占路径及冻结接口；前后批不得重叠开工。

先读取总控、本模块和第一批冻结结果，核对实际提交与上批验收，不从聊天里的旧完成汇报推断当前状态。工作区有未提交内容时先辨明负责者和来源，保留改动，不执行强制重置、清空目录或覆盖式拉取。发现基线不同先登记差异，解决后再实施，不能边写边猜依赖版本。

## 二、修改范围与并行纪律

queries.py、catalog.py、pagination.js 及新增 domain_models、source_state、cache_policy 模块；MCP 注册与命令入口留给 6.1。

本模块对列明路径负责，新增目录也要登记。你并非仓库中的唯一执行者，不撤销他人提交；同批只读公共契约，在独立辅助分支开发，不同时向集成分支推送。同批缺少的实际组件可以用冻结协议的显式夹具开发，夹具不得进入生产默认路径；回接后再核对真实接线。需要修改他人文件时先登记交叉请求，由集成人处理，不能扩大自己的修改范围。

## 三、实施顺序

按下列步骤小步推进，每一步先确定输入、输出与可能副作用，再实现最小可核对改动。保留原有兼容测试，新增用例围绕行为、故障和边界，不写只复制实现细节的空断言。发现失败先定位归属并保留复现；只暂停受影响路径，独立且已授权的工作可继续。修复后重跑受影响检查，不重复运行已经通过且未被新改动影响的整套测试。

1. 核对现有统一查询入口的参数验证、列表快照、文本续读和来源分页，保留老字段与错误码。将新增规范模型作为内部转换层，先兼容现有行为，再扩展新来源；不得为了统一结构丢弃来源特有的状态与检查范围。

2. 统一账号域、来源编号、源记录编号和资源类型组成的稳定键。课程名称、书名、预约位置和标题只用于显示与筛选，不能作为唯一去重依据；没有可靠编号时保留记录并提示无法严格去重。

3. 为结果信封增加明确的来源完整性说明，分别记录来源页数、已取条数、上游总数、快照是否读完和当前查询窗口。达到页数或字节上限时显式部分返回，不能截断后仍报告完整；来源总数缺失时不伪造总数。

4. 统一时间模型，日期、带时区时间、平台本地时间和未知时间分开处理。校园显示默认使用北京时间，固定的日期值不能补成午夜；所有筛选先使用同一查询时刻，分页跨午夜也不能把窗口悄悄换成新的一天。

5. 将缓存策略按资料类型拆分：实时余量每次新查，静态目录短期缓存，业务历史在显式允许时回退。缓存必须绑定账号、参数、来源和原检查时间；没有当前权限证据时不得用旧内容证明已经登录或具备预约资格。

6. 扩展分页和取消机制的测试入口，游标绑定参数及存储格式版本。游标过期、账号切换、参数改变和快照淘汰分别处理；新旧快照不能拼接成一个完整来源，读取取消也不能使未读页面被标成成功。

7. 统一错误翻译，区分未登录、权限不足、来源未支持、学校维护、接口变更、限流及暂时网络失败。内部原因保留稳定分类，公开消息去除令牌、主机和私人路径；调用方可以据分类选择重查或请使用者处理。

8. 为后续适配提供纯函数规范化入口及合成夹具，各服务模块只负责来源读取和字段映射。公共注册表由集成模块统一接线，同批执行者不得为了试用新模型直接添加尚未成熟的外部操作。

## 四、数据与接口约定

标准记录保留 source_id、source_record_id、account_scope、checked_at、date_precision 和原状态映射说明。结果中的 complete、source_complete 与 snapshot_complete 分别定义，任一失败来源都会影响对应聚合完整性；新增字段可选，旧工具输出继续可被原客户端解析。

## 五、异常、退化与兼容

遇到字段冲突或来源版本变化时返回部分数据和原因，不自动选一个看起来更合理的值。未知枚举保留原值的安全摘要及未知状态，不借用邻近状态。异常处理不能把异常文本直接写入公共错误字段。

## 六、必须覆盖的验收用例

用例都使用合成账号、事件、文件和假校园传输；默认拦截外发请求，记录读取与写入次数。本地真实浏览器仅访问合成页面，工程验证不需要真实占座、付款或交作业。测试编码器与生产密钥后端必须可辨别，不能以开启假加密换取通过。跳过检查写明平台原因，未执行、模拟通过和真实业务证据分别记录。

- 来源返回成功空列表时可认定空；登录页、超时和缺页不能认定空。
- 同一标题但不同源编号的记录必须同时保留，并标注可能重复关系。
- 日期只有年月日时，导出和排序不能假定其为当天零点。
- 查询跨午夜续页时，窗口和原检查时间应保持不变。
- 余量缓存不能跨新查询当成实时结果，历史回退必须显式允许。
- 改变参数、账号或快照版本后使用旧游标，必须得到可解释拒绝。
- 取消上游第二页读取时，首段可保留但完整性必须为部分。
- 未知学校状态和敏感异常文本不应被映射成成功或原样公开。

## 七、回退与恢复

保留旧字段和旧入口兼容转换，关闭新增来源注册即可回退；新缓存有独立版本，旧代码不得误读。已返回的游标在回退后允许明确失效，不尝试重新抓取并拼接原快照。

## 八、交付、回接与结束条件

交付模型定义、完整性规范、来源状态分类和跨服务夹具。下游模块应能仅凭信封判断信息是否完整与新鲜，而无需读取某个站点的私有实现细节。

交付安全的模块结果说明与机器可读摘要，包含模块编号、基线、最终提交、负责路径、执行检查、结果和剩余阻塞。原始异常、认证响应、主机信息和用户目录不提交；公开摘要只保留错误类别及合成复现。提交前检查差异与隐私，模块代码及时提交推送，进度更新到原版本计划，不为本模块新建交付 PR。

单模块通过不等于批次通过。集成人按顺序回接同批成果，核对无冲突、无遗漏并完成契约联调后，形成唯一批次提交，才允许下一批开工。常规先执行差异检查和本模块必要用例；批次回接再运行开发检查与全量离线回归，命令沿用 python scripts/dev.py check 和 python scripts/dev.py test。若命令因本批修改变化，先核对兼容说明，不自行换成不覆盖相同行为的简化检查。

遇到缺来源、缺授权或不可恢复冲突时保留明确阻塞，禁止用伪造接口、真实个人数据或弱化保护消除问题。会话到达运行限制前保存已完成步骤、提交、下一条动作和待核对事项；恢复会话后沿用原模块与版本分支。需要 Codex 接手时交出具体范围，整套版本仍由原总任务跟踪。
