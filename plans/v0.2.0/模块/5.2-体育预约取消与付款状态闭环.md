# 5.2 体育预约取消与付款状态闭环

版本目标：Openthu v0.2.0｜批次：5｜状态：待实施方案

【执行方案本体】

## 一、目标与开工条件

强化现有体育办理适配，使团体场地、个人票务、费用、官方验证和取消退款在同一事务中可追踪，但不把付款中、待审批或官方处理中的事项提前称为成功。

必须先取得第4批全部模块（4.1、4.2、4.3、4.4、4.5）验收并回接的集成提交。本批同批模块可并行，仍须遵守独占路径及冻结接口；前后批不得重叠开工。

先读取总控、本模块和第一批冻结结果，核对实际提交与上批验收，不从聊天里的旧完成汇报推断当前状态。工作区有未提交内容时先辨明负责者和来源，保留改动，不执行强制重置、清空目录或覆盖式拉取。发现基线不同先登记差异，解决后再实施，不能边写边猜依赖版本。

## 二、修改范围与并行纪律

sports_actions.py、sports_transport.py 与体育办理测试；查询服务、通用网关及支付系统不在修改范围。

本模块对列明路径负责，新增目录也要登记。你并非仓库中的唯一执行者，不撤销他人提交；同批只读公共契约，在独立辅助分支开发，不同时向集成分支推送。同批缺少的实际组件可以用冻结协议的显式夹具开发，夹具不得进入生产默认路径；回接后再核对真实接线。需要修改他人文件时先登记交叉请求，由集成人处理，不能扩大自己的修改范围。

## 三、实施顺序

按下列步骤小步推进，每一步先确定输入、输出与可能副作用，再实现最小可核对改动。保留原有兼容测试，新增用例围绕行为、故障和边界，不写只复制实现细节的空断言。发现失败先定位归属并保留复现；只暂停受影响路径，独立且已授权的工作可继续。修复后重跑受影响检查，不重复运行已经通过且未被新改动影响的整套测试。

1. 核对当前体育读侧的项目、房间、场地和场次关系，接收完整预检对象。保持场地标识与个人票务模式的区别，缺少来源契约的模式单独禁用，不能用一个场景的请求体套用其他项目。

2. 准备预约时绑定具体日期、场次、参加者、付款方式和确认金额。费用统一以来源声明的最小单位保存，数量、单价和总额分开；无法确认总价时进入官方确认，不用单价乘猜测人数得出应付金额。

3. 执行前重新读取余量、资格、时间、费用和规则，比较预览摘要并核对授权。价格变化、场次关闭、成员或模式变化时重新准备；授权只适用于这一笔，不因同一个人刚刚确认过而对后续场次自动放行。

4. 对验证码、表单、声明和学校付款流程继续使用官方处理路径。插件只展示必要事项与安全入口，不内置打码、绕过实名或自动付款；返回处理后依靠本人订单及详情核对，不以窗口关闭推断操作完成。

5. 细分订单、预约、审批、支付和退款状态，记录来源原值与规范映射。待付款要保留平台期限，退款受理与退款到账分开；失效订单、未支付订单和已取消预约不可简单折叠成同一个完成状态。

6. 取消动作独立生成计划，绑定本人订单、资源、时间、当前付款状态和取消条件。取消失败不自动再次提交，不因按钮消失推断已取消；平台退款是否发生由对应结果确认，不在本地修改付款金额制造一致性。

7. 强化不确定结果核对，处理下单已发送但响应丢失、订单迟到、多条相似订单和详情不完整。重复执行只重查，不能因看不到订单就重新占场；无法唯一匹配时保留未知并提供可继续核对的入口。

8. 给待办和看板输出必要的脱敏摘要与刷新建议，默认不包含成员账号和付款敏感数据。完成合成请求序列、状态及价格变化测试后提交能力表，由公共入口统一登记，不增加体育专用的重复工具集合。

## 四、数据与接口约定

预约结果同时包含业务状态、支付状态、退款状态、检查时间和来源完整性。确认金额采用明确单位和是否已核对的标识；官方跳转链接经过来源和参数脱敏检查，不能直接回传带认证票据的完整 URL。

## 五、异常、退化与兼容

模式未支持、价格变化、资格不足、需要官方验证、付款未知及退款未知分别返回。发生请求超时后保留派发事实，平台限流只影响后续核对节奏，不触发重复下单或取消。

## 六、必须覆盖的验收用例

用例都使用合成账号、事件、文件和假校园传输；默认拦截外发请求，记录读取与写入次数。本地真实浏览器仅访问合成页面，工程验证不需要真实占座、付款或交作业。测试编码器与生产密钥后端必须可辨别，不能以开启假加密换取通过。跳过检查写明平台原因，未执行、模拟通过和真实业务证据分别记录。

- 预览后单价或数量变化，旧计划必须失效而非按新价格自动提交。
- 不同项目的同名场地不能互换标识或请求模式。
- 官方验证尚未完成时，状态应保留待官方处理。
- 已下单待付款和已付款待审批必须分别呈现。
- 重复调用同一个未决计划，合成派发计数只能为一次。
- 取消成功但退款未确认时，不得声称已经到账。
- 订单列表缺页或存在两笔近似记录时，不能选任意一笔判成功。
- 关闭新办理开关后，已有订单查询及结果核对仍须工作。

## 七、回退与恢复

停用新预约与取消入口，保持订单读取和原事务适配器可用。回退不产生自动退款或二次取消；保留未决订单及官方处理引用，避免用户在恢复后失去核对入口。

## 八、交付、回接与结束条件

交付各模式启用清单、金额与状态模型、官方衔接及恢复测试。既有校园验证要求始终保留，完成模拟闭环不能被描述成已经替使用者完成真实付款和退款。

交付安全的模块结果说明与机器可读摘要，包含模块编号、基线、最终提交、负责路径、执行检查、结果和剩余阻塞。原始异常、认证响应、主机信息和用户目录不提交；公开摘要只保留错误类别及合成复现。提交前检查差异与隐私，模块代码及时提交推送，进度更新到原版本计划，不为本模块新建交付 PR。

单模块通过不等于批次通过。集成人按顺序回接同批成果，核对无冲突、无遗漏并完成契约联调后，形成唯一批次提交，才允许下一批开工。常规先执行差异检查和本模块必要用例；批次回接再运行开发检查与全量离线回归，命令沿用 python scripts/dev.py check 和 python scripts/dev.py test。若命令因本批修改变化，先核对兼容说明，不自行换成不覆盖相同行为的简化检查。

遇到缺来源、缺授权或不可恢复冲突时保留明确阻塞，禁止用伪造接口、真实个人数据或弱化保护消除问题。会话到达运行限制前保存已完成步骤、提交、下一条动作和待核对事项；恢复会话后沿用原模块与版本分支。需要 Codex 接手时交出具体范围，整套版本仍由原总任务跟踪。
