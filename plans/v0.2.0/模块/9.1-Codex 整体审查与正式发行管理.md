# 9.1 Codex 整体审查与正式发行管理

版本目标：Openthu v0.2.0｜批次：9｜状态：待实施方案

【执行方案本体】

## 一、目标与开工条件

由 Codex 对整个候选做独立审查，确认实现、证据、隐私和分发一致后发布正式零点二版本，并保留后续维护和人工接手入口，避免用模块报告或一组绿灯替代整体质量判断。

必须先取得第8批全部模块（8.1）验收并回接的集成提交。本批为单模块串行关口，不与前后批重叠执行。

先读取总控、本模块和第一批冻结结果，核对实际提交与上批验收，不从聊天里的旧完成汇报推断当前状态。工作区有未提交内容时先辨明负责者和来源，保留改动，不执行强制重置、清空目录或覆盖式拉取。发现基线不同先登记差异，解决后再实施，不能边写边猜依赖版本。

## 二、修改范围与并行纪律

Codex 审查结论、必要修复回接、受保护主分支合并、标签与 Release、公开资产验证及维护记录；本批串行执行。

本模块对列明路径负责，新增目录也要登记。你并非仓库中的唯一执行者，不撤销他人提交；同批只读公共契约，在独立辅助分支开发，不同时向集成分支推送。同批缺少的实际组件可以用冻结协议的显式夹具开发，夹具不得进入生产默认路径；回接后再核对真实接线。需要修改他人文件时先登记交叉请求，由集成人处理，不能扩大自己的修改范围。

## 三、实施顺序

按下列步骤小步推进，每一步先确定输入、输出与可能副作用，再实现最小可核对改动。保留原有兼容测试，新增用例围绕行为、故障和边界，不写只复制实现细节的空断言。发现失败先定位归属并保留复现；只暂停受影响路径，独立且已授权的工作可继续。修复后重跑受影响检查，不重复运行已经通过且未被新改动影响的整套测试。

1. 核对候选提交、树、版本计划和所有验收证据，独立检查高风险改动及关键调用链。优先审查密钥来源、跨进程明文边界、宿主授权、上传副作用、未知结果恢复和本地看板访问控制，不能只根据 Hermes 的完成汇报批准版本。

2. 复核受条件约束的新能力，检查其依据、启用情况与公开说明一致。没有来源契约的适配不允许被描述为已支持；若与原版本承诺冲突，明确向使用者说明所需范围决定，保留候选状态直至问题处理。

3. 审查发现问题后在原版本 PR 中给出可复现原因、影响与修复要求，Hermes 在同一批次继续修改。需要 Codex 接手时明确范围和辅助分支，修复后回接同一候选并重验受影响部分，不另拆一串小发行。

4. 复查发行内容及提交元数据，使用项目公共署名与经过确认的隐私邮箱策略。不得为合并而把私人邮箱、机器路径和原始日志写入公开历史；保护规则和维护操作应保留记录，完成后保持主分支检查要求有效。

5. 在受保护分支的既定流程下合并已审查候选，核对合并结果与已检查源码树一致。若合并后内容变化，应重新验证相关范围；正式标签必须指向批准的提交，不能指向仍包含未提交或未经检查改动的工作区。

6. 从批准的源码重新生成正式资产或严格核对候选资产等价性，验证版本、依赖、许可证、资源清单和校验值。准备中文发行说明，明确新增能力、迁移要求、已知限制和未决真实业务状态，不将工程测试写成学校业务已成功。

7. 创建正式 GitHub Release 并上传完整源码、安装构建包、校验清单和安全验证摘要。使用无需个人授权的公开下载路径逐个核验资产，检查实际字节及哈希，不在报告中泄露带临时签名的下载重定向链接。

8. 更新版本总任务与维护记录，保留尚未解决问题、条件适配和下一版方向。通知使用者正式版本地址和后续手动接手方式；不向 Hermes 自动派发下一轮任务，不创建后台监控、定时生成或抢占预约的程序。

## 四、数据与接口约定

发行记录包含批准提交、合并提交、标签、源码树、资产名称、大小、哈希和公开验证结果。真实业务证据等级沿用原始事实，源码审查与安装检查不能把未知写入状态提升为真实成功。

合并前确认可公开的署名策略，不向 GitHub 传入猜测或未验证的邮箱。若服务端署名可能带入私人信息，应保留候选并解决身份设置，不以泄露私人邮箱或长期关闭仓库保护来换取合并成功。

## 五、异常、退化与兼容

代码缺陷、隐私泄露、资产错版、公开下载失败或校验不符都必须停止或修正发行。已经公开的错误资产应有透明修订记录，不能删除当前文件后假装问题未发生；身份信息问题先避免继续传播，再按实际来源处理。

## 六、必须覆盖的验收用例

用例都使用合成账号、事件、文件和假校园传输；默认拦截外发请求，记录读取与写入次数。本地真实浏览器仅访问合成页面，工程验证不需要真实占座、付款或交作业。测试编码器与生产密钥后端必须可辨别，不能以开启假加密换取通过。跳过检查写明平台原因，未执行、模拟通过和真实业务证据分别记录。

- 检查审查结论对应最终提交，而不是过期的模块分支。
- 高风险路径应有独立复核与回归证据，不能只看总通过数。
- 正式标签、源码树与批准候选必须一致或有明确重验记录。
- 每个公开下载资产都应无需私人令牌且与校验清单一致。
- 归档和提交元数据不得出现维护者私人邮箱、目录或认证值。
- 能力说明须准确区分已实现、已启用、已核对及未知业务状态。
- 发行失败时原稳定版本和必要恢复运行时仍可获取。
- 版本发布后没有自动开始下一轮 AI 调度或校园业务操作。

## 七、回退与恢复

出现发行缺陷先限制错误版本传播并保留说明，提供已验证旧版本或修订版。程序回退与真实业务取消仍分开，保留受影响状态、密钥和未决事务的恢复能力，不承诺撤销平台已经受理的操作。

## 八、交付、回接与结束条件

交付正式版本、公开可验证资产、完整审查记录和后续维护清单。完成条件是发布内容与批准实现一致且使用者能下载校验，不能仅凭创建了一个 Release 页面就标记整个升级成功。

交付安全的模块结果说明与机器可读摘要，包含模块编号、基线、最终提交、负责路径、执行检查、结果和剩余阻塞。原始异常、认证响应、主机信息和用户目录不提交；公开摘要只保留错误类别及合成复现。提交前检查差异与隐私，模块代码及时提交推送，进度更新到原版本计划，不为本模块新建交付 PR。

单模块通过不等于批次通过。集成人按顺序回接同批成果，核对无冲突、无遗漏并完成契约联调后，形成唯一批次提交，才允许下一批开工。常规先执行差异检查和本模块必要用例；批次回接再运行开发检查与全量离线回归，命令沿用 python scripts/dev.py check 和 python scripts/dev.py test。若命令因本批修改变化，先核对兼容说明，不自行换成不覆盖相同行为的简化检查。

遇到缺来源、缺授权或不可恢复冲突时保留明确阻塞，禁止用伪造接口、真实个人数据或弱化保护消除问题。会话到达运行限制前保存已完成步骤、提交、下一条动作和待核对事项；恢复会话后沿用原模块与版本分支。需要 Codex 接手时交出具体范围，整套版本仍由原总任务跟踪。
