# 6.3 完整发行布局与安装升级迁移

版本目标：Openthu v0.2.0｜批次：6｜状态：待实施方案

【执行方案本体】

## 一、目标与开工条件

解决完整源码包与 Python 安装包的能力分裂，统一资源定位、依赖声明、升级与回退，使用户从正式交付物安装后能够得到声明的功能，而不依赖开发者的源码目录。

必须先取得第5批全部模块（5.1、5.2、5.3、5.4）验收并回接的集成提交。本批同批模块可并行，仍须遵守独占路径及冻结接口；前后批不得重叠开工。

先读取总控、本模块和第一批冻结结果，核对实际提交与上批验收，不从聊天里的旧完成汇报推断当前状态。工作区有未提交内容时先辨明负责者和来源，保留改动，不执行强制重置、清空目录或覆盖式拉取。发现基线不同先登记差异，解决后再实施，不能边写边猜依赖版本。

## 二、修改范围与并行纪律

pyproject.toml、MANIFEST.in、requirements-dev.txt、配置生成和打包脚本、发行依赖锁；本模块独占包元数据与资源清单。

本模块对列明路径负责，新增目录也要登记。你并非仓库中的唯一执行者，不撤销他人提交；同批只读公共契约，在独立辅助分支开发，不同时向集成分支推送。同批缺少的实际组件可以用冻结协议的显式夹具开发，夹具不得进入生产默认路径；回接后再核对真实接线。需要修改他人文件时先登记交叉请求，由集成人处理，不能扩大自己的修改范围。

## 三、实施顺序

按下列步骤小步推进，每一步先确定输入、输出与可能副作用，再实现最小可核对改动。保留原有兼容测试，新增用例围绕行为、故障和边界，不写只复制实现细节的空断言。发现失败先定位归属并保留复现；只暂停受影响路径，独立且已授权的工作可继续。修复后重跑受影响检查，不重复运行已经通过且未被新改动影响的整套测试。

1. 盘点程序运行真正需要的 Python、Node、认证辅助、锁文件、静态界面和许可证。区分运行时依赖、开发工具及可选浏览器功能，补齐缺项；不能让普通安装必须依赖测试框架，也不能把 node_modules 和本机虚拟环境直接塞入发行包。

2. 依据统一路径接口设计包内资源位置，将仓库级运行依赖作为受控资源纳入完整 wheel 和 sdist，或通过明确的完整安装资产机制提供。首选单一源清单生成两种布局，禁止复制两套会随修改逐渐不一致的网关和辅助代码。

3. 修正包内执行路径，安装后从资源描述中发现 Node 辅助与固定上游代码，不再按源码父目录层级硬编码。资源只读，所有状态在用户私有目录；升级程序文件不会覆盖凭据、会话、下载与未决事务。

4. 锁定经过验证的依赖范围、完整性和许可证，Node 安装采用明确来源与禁止未知生命周期脚本的方式。浏览器安装是可说明的独立步骤，缺浏览器时诊断应清楚；禁止为了首装方便下载并执行不可追溯的远程脚本。

5. 重构打包脚本，从已提交的 Git 内容或等价受控清单取文件，规范时间、权限、顺序与路径，避免不同工作区换行导致源码归档不一致。发行版本来自统一版本源，包、工具版本、说明和标签应能相互核对。

6. 建立旧状态与配置迁移预览，列出格式、目标、兼容性和是否需要重新建立认证。旧 Windows 密文不导往 Linux 解密，真实凭据不进入代码快照；迁移遇到新旧状态冲突时保留双方并要求明确选择，不静默覆盖。

7. 实现源码包、wheel 和 sdist 的全新目录恢复安装检查，工作目录切离仓库后运行静态目录与代表性合成流程，确认没有借用开发者 PYTHONPATH。静态看板资源按冻结资产清单接入，前端完成后由集成批补做整体构建。

8. 为正式发行生成源码、构建包、校验清单、依赖与许可证说明及可读升级指南。本模块只准备候选产物和构建流程，不发布 GitHub Release；最终公开资产由 Codex 审查后上传并验证。

## 四、数据与接口约定

发行清单记录版本、提交、资源逻辑名、安装位置和哈希，排除环境配置、缓存、日志、密钥和个人数据。状态格式版本与产品版本分别管理，回退兼容性必须显式声明，不能仅凭版本号大小推断。

## 五、异常、退化与兼容

缺资源、哈希不符、依赖未满足、只读目录和迁移冲突分别阻止相关操作。构建失败不得沿用旧包冒充新版本，打包脚本必须拒绝未提交的发行源码和不在允许清单中的文件。

## 六、必须覆盖的验收用例

用例都使用合成账号、事件、文件和假校园传输；默认拦截外发请求，记录读取与写入次数。本地真实浏览器仅访问合成页面，工程验证不需要真实占座、付款或交作业。测试编码器与生产密钥后端必须可辨别，不能以开启假加密换取通过。跳过检查写明平台原因，未执行、模拟通过和真实业务证据分别记录。

- 在仓库外的新环境安装 wheel，资源解析不能回退到开发源码目录。
- 从 sdist 重建后，必要辅助、锁文件和许可证应完整存在。
- 构建目录中放入假密钥、缓存和日志，它们不得进入任何归档。
- 改变工作区换行或文件时间后，受控源码归档应保持相同内容规则。
- 旧格式状态升级失败时，原有效文件和未决日志必须保留。
- 缺 Node 或浏览器时，诊断应指出具体能力而不是笼统安装成功。
- 版本号、包元数据、校验清单和候选发布说明必须一致。
- 重新安装程序后，使用者下载文件和私人状态不应被改写。

## 七、回退与恢复

发行失败保留上一稳定版本资产和迁移前状态，安装修复只替换程序资源。回退前检查新状态是否能被旧运行时读取，必要时保留独立恢复工具；不通过删除用户目录来获得干净安装结果。

## 八、交付、回接与结束条件

交付可独立安装的发行布局、固定资源清单、构建与恢复检查。完整包必须具备所声明的资源，若仍存在单独 wheel 的限制应作为发布阻塞明确处理，不能仅在说明中重复旧缺陷然后声称已解决。

交付安全的模块结果说明与机器可读摘要，包含模块编号、基线、最终提交、负责路径、执行检查、结果和剩余阻塞。原始异常、认证响应、主机信息和用户目录不提交；公开摘要只保留错误类别及合成复现。提交前检查差异与隐私，模块代码及时提交推送，进度更新到原版本计划，不为本模块新建交付 PR。

单模块通过不等于批次通过。集成人按顺序回接同批成果，核对无冲突、无遗漏并完成契约联调后，形成唯一批次提交，才允许下一批开工。常规先执行差异检查和本模块必要用例；批次回接再运行开发检查与全量离线回归，命令沿用 python scripts/dev.py check 和 python scripts/dev.py test。若命令因本批修改变化，先核对兼容说明，不自行换成不覆盖相同行为的简化检查。

遇到缺来源、缺授权或不可恢复冲突时保留明确阻塞，禁止用伪造接口、真实个人数据或弱化保护消除问题。会话到达运行限制前保存已完成步骤、提交、下一条动作和待核对事项；恢复会话后沿用原模块与版本分支。需要 Codex 接手时交出具体范围，整套版本仍由原总任务跟踪。
