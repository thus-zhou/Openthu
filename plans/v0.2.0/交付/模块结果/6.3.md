## 边界与限制

- 本机只跑 Linux；Windows 结果来自 run `44076049516` 的 `windows-2025` job（Python 1327 通过 /
  14 跳过 / 0 失败、Node 66 通过），未在本地 Windows 主机复现。真实 Windows DPAPI 认证、
  Windows 上的真实迁移不在本模块验证范围。
- wheel 不含 `node_modules` 与离线测试：安装后需要时在包目录执行 `npm ci --ignore-scripts`，
  `openthu-doctor`/`doctor` 的 Node 检查会指出；`scripts/dev.py` 只在源码包中。
- 依赖锁定到直接依赖的精确版本与许可证；未生成传递依赖哈希锁（需要联网解析各平台 wheel），
  完整性由产物 `SHA256SUMS` 与 Node `package-lock.json` 的 integrity 提供。
- 源码归档从 Git 对象生成：未提交的改动不会进入候选，构建前必须先提交；`verify` 因此能发现
  旧树产物，但也要求“先提交、后构建”。
- `install-check` 使用带 `--system-site-packages` 的临时虚拟环境以便离线解析运行时依赖；
  它证明布局、入口、自检与“不改写用户状态”，不证明真实校园认证。
- 迁移只做文件级复制：不重放未决事务，不迁移跨平台 DPAPI 密文，不复制主机授权密钥与 grant，
  不删除、不移动旧目录；`actions-v1/`、`submissions-v1/` 的记录仍需人工核对后按具体事项重新授权。
- `THU-TODOS-1`/`THU-ACTION-1` 外层容器格式未改，仍属 6.1/8.1 的存储步骤。
- 未更新 `plans/v0.2.0/交付/模块负责表.*`、`批次门禁.*`、`VERSION_MANIFEST.json` 的模块状态，
  避免与同批 6.1/6.2 并行修改共享台账；本模块只交付自己的模块结果文件。
- 未新建 PR、未合并 main、未打标签、未发布；`release-manifest.json` 明确
  `release_status=candidate-not-released`、`published=false`。
