- `scripts/package_release.py`：`build|verify|install-check|manifest`。
  - `build` 从 Git 对象（`ls-files -s` + `cat-file --batch`）读取已提交内容，工作区换行、
    文件时间与未跟踪文件都不参与；跟踪树不干净直接 `RELEASE_TREE_DIRTY`。
  - 源码 `zip`/`tar.gz` 固定时间、模式、属主、排序与压缩级别；sdist 生成后再规范化重打包，
    去掉构建账户的 uid/gid/用户名与时间。
  - `verify` 核对版本、`SHA256SUMS`、wheel 元数据（名称、版本、`Requires-Python`、
    `Requires-Dist`、6 个入口点）、包内 `layout.json`、逻辑资源与哈希、许可证、禁止文件、

  - `install-check` 在仓库外的临时虚拟环境安装 wheel，以隔离解释器从其他目录运行，
    断言 `source_root` 为空、认证资源来自 `_bundled`，并启动 29 个 MCP 工具。
  - 写出 `release-manifest.json`：版本、提交、产物 SHA256/大小、源码统计、每个运行资源的

## 边界与限制

- 本机只跑 Linux；Windows 结果来自 `44059743559` 的 CI（Python 1306 通过 / 13 跳过 / 0 失败），
  未在本地 Windows 主机复现；Windows 真实 DPAPI 认证不在本模块验证范围。
- wheel 不含 `node_modules` 与离线测试：安装后仍需 `python scripts/dev.py setup-node`（或
  `npm ci --ignore-scripts`），`doctor` 的 `node-runtime` 会指出。
- 依赖锁定到直接依赖的精确版本与许可证；未生成传递依赖的哈希锁（需要联网解析每个平台的
  wheel），因此“完整性”目前通过产物 `SHA256SUMS` 与 Node `package-lock.json` 的 integrity 提供。
- 源码归档从 Git 对象生成，未提交的改动不会进入：这既是保证，也意味着构建前必须先提交。
- `install-check` 使用 `--system-site-packages` 的临时虚拟环境以便离线解析运行时依赖；
  它证明的是布局与入口可用，不是真实校园认证。
- 迁移只处理文件级复制：不重放未决事务，不迁移跨平台 DPAPI 密文，不删除、不移动旧目录；
  `actions/` 的未决记录仍需人工核对后按具体事项重新授权。
- `THU-TODOS-1`/`THU-ACTION-1` 外层容器格式未改，仍属 6.1/8.1 的存储步骤。
- 未更新 `plans/v0.2.0/交付/模块负责表.*`、`批次门禁.*`、`VERSION_MANIFEST.json` 的模块状态，
  避免与同批 6.1/6.2 并行修改共享台账；本模块只交付自己的模块结果文件，批次回接时统一更新。
- 未新建 PR、未合并 main、未打标签、未发布；`release-manifest.json` 明确
  `release_status=candidate-not-released`、`published=false`。
