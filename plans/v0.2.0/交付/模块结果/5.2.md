## 行为约定

1. **预检快照绑定**：`selected_slot` 在选中的余量页上调用
   `precheck.build('sports','availability',...)`，用摘要和选中场地/场次的预检块生成
   `slot_binding`。绑定只取稳定字段（资源编号、窗口、可用状态、容量、费用分值、规则值、
   表单部署），不含 `checked_at`/`source`；同一快照隔一段时间仍可执行，而单价、应付总额、
   场次时间、余量状态、取消规则、模式或容量任一变化都会改变指纹。
2. **精确的项目/场地/模式**：先读项目目录确认 `sceneUseType`；声明模式与请求模式不符时
   在任何模式相关分页请求之前拒绝（`INVALID_ARGUMENTS`）。跨项目同名场地的拒绝由 4.3
   只读层提供（`field_row` 校验 `sceneUuid`），写入侧只绑定已选中的 id 和请求体；本模块
   不再重复恒真的断言。请求体绑定 `sceneUuid`、`siteUuid`、`siteType`、`sceneUseType`、
   `sessionDetailUuid` 和精确时段。
3. **模式能力表**：仅 `SPORT_GROUP` 与 `SPORT_PERSON` 有来源契约；未登记模式直接拒绝，
   不复用另一模式的请求体。`SPORT_PERSON` 固定 1 张、仅本人，并且始终附带
   `CHOOSE_TICKET_AND_QUANTITY` 官方交接，不直接派发。多人票/多张票不在本适配器输入
   契约内，必须走官方页面。
4. **金额**：费用只接受非负整数分；预览文本分列数量、单价和总额，展示值用整数除法精确
   到分，不做浮点或二次乘 100。应付总额只采用来源声明的 `payableAmount`；来源未声明
   总额时进入官方结算确认，绝不用“单价 × 猜测人数”生成金额。计划带有
   `expected_total_fen` 时与来源总额比对，不一致即 `SPORTS_FEE_CHANGED`；免费计划在
   来源出现非零单价/总额时同样拒绝。文案与结构化证据一致：显式计划金额才写“已按计划
   金额核对”，免费计划写“按 0 元核对”，付费但未给计划金额写“未提供计划金额，未做比对”。
5. **官方验证与付款**：验证码、表单、部署标识和学校付款流程继续使用官方路径。预览只
   展示必要事项与安全入口，不内置打码、绕过实名或自动付款；出现验证码/表单/部署不确定
   时计划状态为 `AWAITING_OFFICIAL` 且不派发。执行后结果依赖本人订单与详情，不以页面
   窗口关闭推断完成。
6. **状态轴与闭环**：预约阶段、审批、付款、退款四轴继续由 4.3 的只读映射给出；办理证据
   同时保留来源原值（`platform_status`/`approval_status`/`payment_status`/`refund_status`）
   和规范状态、`state_confirmed`。待付款保留平台期限（`payment_deadline` 与
   `payment_deadline_state`）；退款分 `refund_accepted`、`refund_settled_by_platform`
   和 `refund_arrived_verified`，后者恒为 `false`。付款过期（`PAYMENT_EXPIRED`）或付款
   取消（`PAYMENT_CANCELLED`）会把本计划判为 `FAILED`，不会被折叠成成功或永久未知。
7. **取消计划**：取消独立生成计划，绑定本人订单号、项目、场地集合、起止时间、当前预约/
   审批/付款/退款状态、已付/总额和取消提前量。**已生效（`RESV_EFFECT` + 审批通过）的常规
   订单可以生成取消计划**：`RESV_EFFECT` 追加 `OFFICIAL_CANCEL_CONTROL`，已付款或退款/
   付款未知再追加 `CONFIRM_REFUND_CONSEQUENCES`，计划进入 `AWAITING_OFFICIAL`，由用户在
   官方页面完成并在 `result` 中核对。只有已结束、已取消、已过期或来源状态无法映射的订单
   会在计划生成前被拒绝。场地列表绑定在计划指纹中，但不再作为公开字段回传（公开预览不
   出现被打码的 `site_ids`）。
8. **未决核对**：创建响应丢失后只在 `dispatch_at` 起 24 小时内核对（`gmtCreate` 必须在
   派发之后），避免把很久以后的无关订单算到本计划。匹配要求恰好一条远端记录，并再次
   读取详情比较扩展状态、平台状态、总额和付款方式；缺页、重复页、两条近似记录、详情
   不一致或**看起来像本计划的**坏记录都返回 `complete=false`。无关的畸形历史订单只被
   忽略，不阻断本次核对；畸形 `gmtCreate` 不会抛异常打断核对。重复执行只重新核对，不
   重新占场；无法唯一匹配时 `next_actions` 只有重查入口。
9. **派发事实与未观测请求**：适配器在派发前向 4.4 的副作用台账登记 `official_request`
   （`NOT_SENT`），在**单次门禁接受请求的那一刻**登记 `SENT`（早于 fetch 响应）。响应
   丢失、进程被杀都保留 `SENT`。若页面 fetch 已返回但 `page.route` 从未观察到请求（例如
   Service Worker 接管），不再报“确定未派发”，而是抛 `SPORTS_DISPATCH_UNOBSERVED`，事务
   状态保持 `UNKNOWN`、台账记为 `UNKNOWN`；只有路由观察到并拒绝、或页面根本没有发起
   fetch（`NO_PENDING`）时才是确定未派发。派发前的重读/签名准备失败也转为确定未派发。
10. **脱敏与兼容**：证据的 `platform` 只含本人预约号、状态、金额、期限、支付方式观测值
    和刷新建议，不含成员账号或付款凭据；官方链接只输出登记路由；`checked_at` 统一为 UTC
    （`checked_at_zone=UTC`）。旧操作名、参数、字段名和状态字符串保持兼容；`fee`/
    `cancel_rule` 的文案在本次修复中更新，字段名与类型不变。停用写入开关后只读查询、
    `describe` 和未决事务核对继续工作；`THU_SPORTS_READ=0` 会暂停未决事务的核对读取。

## 金额与状态模型

| 来源 | 规范 | 说明 |
|---|---|---|
| `resvStatus` | `reservation` 轴 | `RESV_EFFECT`/`RESV_UNEFFECT`/`RESV_END`；未知值保留 `UNKNOWN` 和摘要 |
| `resvCheckStatus` | `approval` 轴 | 待审批/审批中/通过；审批中不升级为成功 |
| `orderStatus` | `payment` 轴 | 待付款、处理中、已付款、付款取消、付款过期；过期/取消使计划 `FAILED` |
| `orderRefundStatus` | `refund` 轴 | `NONE`/`REQUESTED`/`REFUNDING`/`REFUNDED`/`REJECTED`/`FAILED`/`PENDING`/`MANUAL` |
| `resvExtendStatus` 位 2 | 取消位 | 只用于整体取消结论，不足以证明退款到账 |
| `resvExtendStatus` 位 256 | 官方控制（假设） | 防御性交接；没有来源样本，能力表登记为 `assumptions` |
| `cancelBeforeStart` | `MINUTE` 规则 | 缺失则要求官方核实，不推算期限 |
| `chargingUnitPrice`/`payableAmount`/`paidAmount`/`totalAmount` | `FEN` | 只接受非负整数；展示用精确整数除法 |
| `orderInfo.payType` | 未验证域 | 请求/响应枚举域缺少来源证据；只记录观测值，不阻断记录匹配 |

事务引擎状态：`PENDING_PAYMENT`（已下单待付款）与 `PENDING_APPROVAL`（已付款待审批）
分别呈现；`SUCCEEDED` 只表示远端记录与计划精确匹配；取消成功不表示退款到账。

## 保留边界

- 全部为离线合成验证：没有真实登录、余量读取、预约创建、取消、付款或退款；`SUCCEEDED`
  只表示合成远端记录与计划匹配。
- `sports-action-v1` 的输入 schema 由 4.4 冻结：没有数量参数，团体项目固定 1 场、个人票务
  固定 1 张且仅本人；多张票、多人票和改期不在本适配器范围内，必须走官方页面。
- 计划 `business` 字段仍是字符串 schema；数量/单价/总额在预览文本中分列，结构化金额在
  结果 `platform.amounts`（单位 `FEN`，`total_verified` 表示是否与计划金额比对）。
- `payType` 的请求/响应枚举域没有真实样本；当前只记录观测值并做软匹配，不把它当作已证实
  的来源形态。真实创建前需要本机核对。
- `resvExtendStatus` 位 256 的“官方控制”含义是防御性假设，没有来源样本；命中时走官方
  页面而不是直接派发。
- 迟到的订单只在派发后 24 小时内核对，且要求 `gmtCreate`；缺 `gmtCreate` 或早于派发的
  订单不会被算作本计划结果。24 小时后若仍未找到记录，计划保持 `UNKNOWN`（P2-7 的框架
  终态尚未提供）。
- 取消核对以本人记录号、项目、精确起止时间确认；场地列表在准备阶段绑定进指纹，取消
  成功后的核对不再单独比较场地 id（该比较只影响计划失效，不影响记录身份）。
- `refund_arrived_verified` 恒为 `false`；`refund_settled_by_platform` 只代表平台退款枚举，
  不代表银行/支付渠道到账。
- 订单列表持续短页/重复页/超过 50 页时仍拒绝准备新预约；一次瞬时短页会自动重读一次。
- `THU_SPORTS_READ=0` 会暂停未决事务核对；`THU_SPORTS_WRITE=0` 只停新办理，保留核对。
- 未修改 `sports.py`、`queries.py`、`actions.py`、`action_store.py`、`browser.py` 或
  `mcp_stdio.py`；跨项目同名场地保护、订单读取和四轴映射仍由 4.3 提供。
- 9 个 sports 错误码是本次新增登记；`source_state.py` 与 `error-classification.json`
  的修改为只增，属于 1.1/3.2 的顺序交接。
