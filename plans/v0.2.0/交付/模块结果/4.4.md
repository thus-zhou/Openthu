### 新增 `consent/`

- `protocol.py`：`host-authorization-v1` 纯函数协议。授权绑定 `plan_id`、`account`、
  业务 `digest`、`adapter_version`、计划创建时生成的 64 位十六进制一次性挑战值、
  `issued_at`/`expires_at`、`source=human` 与宿主事件引用，使用 HMAC-SHA256 签名；
  校验顺序为版本、签名（恒定时间比较）、账号、适配器、计划/摘要/挑战值、来源、引用、
  时间。错误只含类别。
- `store.py`：宿主密钥与待用授权文件使用与事务日志相同的 `protect`/`unprotect`；
  密钥容器 `THU-CONSENT-KEY-1`，授权容器 `THU-CONSENT-1`，POSIX 0600，原子写入并
  回读校验。`peek` 只读校验，`take` 在预检成功后才消费，`discard` 清理遗留；
  密钥缺失时失败关闭，不生成替代密钥。
- `cli.py` / `__main__.py`：`python -m thu_assistant.consent --plan <operation_id>`
  本机确认入口，逐项显示全部业务字段（含区域/座位/房间/场馆/场地/场次编号）和业务摘要
  前 12 位，只有输入大写 `CONFIRM` 才签发；无交互终端返回
  `SPECIFIC_HUMAN_AUTHORIZATION_REQUIRED`。旧记录缺少挑战值时先本地补一个再签发。
- `README.md`：授权字段、签发路径、拒绝语义、状态表、请求门禁、副作用清单、
  回退与跨模块接线；已随 `package-data`/`MANIFEST.in` 进入发行包。

### 修改

- `actions.py`
  - 计划新增一次性 `challenge`、`consent_protocol` 和 `effects`；公开结果新增
    `effects`、`state_history`（最近 20 条）、`event_count`、`next_actions` 与
    `local_confirmation_command`，不暴露挑战值、签名或业务原值。
  - 新增 `STATE_ENTRY`/`describe_states()`，明确九个状态的进入条件、授权消费状态
    与远端写入可能；`TRANSITIONS` 保持原语义。
  - 新增 `SideEffectLedger`（`declare`/`sent`/`unknown`，只允许
    `NOT_SENT → SENT → UNKNOWN`，终态拒绝继续修改，最多 50 步），绑定到当前
    `DISPATCHING` 记录和进程；适配器以 `accepts_ledger = True` 显式选择。
  - 授权证据：签名授权直接验签；进程内的旧式确认字典先规范化为签名、绑定挑战值的
    授权再落盘。`DECLINED` 与 Windows 原生消息框返回 `None` 都是明确拒绝并删除待用
    授权；`NOT_APPLICABLE`（以及非 Windows 的原生回调）才回退到待用授权；其他回调
    返回 `None` 表示没有证据，本次拒绝且不回退。
  - 授权只在预检成功后消费；临时预检失败不会摧毁人工确认，可直接重试。
  - 预检精确比较业务摘要、页面上下文和附件标识列表；任一项变化即
    `PRECONDITIONS_CHANGED_PREPARE_AGAIN`。
  - 认领、失效、核对与中断恢复使用带修订号的条件更新；`DISPATCHING`、授权证据和
    进程号在派发前原子落盘。`NotDispatched` 只有在请求计数为零且副作用清单没有
    `SENT`/`UNKNOWN` 时才归为“确定未发出”。
  - 状态、原因和远端记录都未变化时不写日志、不追加事件；并发核对冲突改为读取最新
    记录，`result()` 的恢复路径同样兜底。
- `action_store.py`：`update(..., expected_revision=...)` 条件更新；读取时校验
  挑战值、副作用清单与协议字段；本地读写失败分类为 `STATE_READ_FAILED` /
  `STATE_WRITE_FAILED`；旧记录缺少新字段仍可读。
- `action_recovery.py`：离线盘点增加 `ok`、`readable`、`unreadable`、逐文件错误类别、
  `effects`、`pending`、`cancellation=NOT_PERFORMED` 与 `read_only=true`；单个日志
  损坏或属于其他 Windows 用户时仍列出其余事务，不访问网络、不调用适配器、不取消。
- `browser.py`：通用表单预览只在存在可执行适配器时给出授权协议和本机确认命令；
  `ADAPTER_REQUIRED` 计划改为提示等待适配器，提交仍被拒绝。

## 安全结果摘要

- 授权只对一笔计划有效；挑战值、签名和宿主事件引用只存在于加密日志与授权文件，
  不进入公开结果、普通日志或 URL。授权预检成功后才消费，成功 / 拒绝 / 计划过期都会
  清理遗留文件。
- 无交互终端、拒绝、伪造签名、错误账号/计划/摘要/适配器版本、过期授权均不派发；
  缺失有效证据时计划保持 `PREPARED`，由使用者在本机确认。
- 进程内旧式确认字典在存储前被规范化为签名、挑战值绑定的授权；没有签名证据不会
  进入日志或派发。
- `DISPATCHING` 与授权证据先落盘再发送；落盘失败时远端请求计数为零。
- 认证令牌可在适配器构造请求时刷新；业务摘要、上下文或附件哈希变化必须重新准备。
- 终态、未决和未知状态都不能自动重发；`UNKNOWN` 只提供核对入口；无变化轮询不改写
  日志。
- 回退盘点只读、逐文件报告错误，输出不含业务原值，`cancellation=NOT_PERFORMED`，
  删除本地日志不会被当作远端取消。
- 未接入真实校园站点；没有新增生产适配器，没有开启真实写入。

## 剩余边界

- 外层 `THU-ACTION-1` 容器与 `operation_id.dpapi` 文件名保持不变；2.2 的新封套已嵌套
  在内，但把稳定 `record_id` 绑定进 AAD 的存储迁移未在本模块完成，留给后续存储/集成
  阶段。
- 进程内 `consent_verifier` 的旧接口仍被接受，但其结果会先规范化为签名授权；没有
  签名或挑战值的证据不会落盘。
- 并发执行同一计划时，未抢到一次性授权的重复调用会安全失败（不派发）；先到者最多
  发送一次，重复调用应查询结果。
- `attachments` 字段由具体适配器的业务契约定义；当前契约拒绝该字段，附件身份比较是
  5.3 的扩展点，摘要已覆盖现有业务字段。
- 本模块没有修改 `docs/contracts/action-boundaries.md`（`docs/` 归 7.3）；授权协议文档
  放在 `src/thu_assistant/consent/README.md`，7.3 汇总时可引用或迁移。
- 真实预约、取消、续借、付款与交作业仍未实现，属于第 5 批；本模块不声称任何真实
  校园写入能力。
- Windows 原生消息框仍返回旧式字典；引擎会规范化，5.2 可直接调用 `issue_for` 以简化
  证据链。
