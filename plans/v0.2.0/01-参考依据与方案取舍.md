# 参考依据与方案取舍

本文件是来源索引与决策说明，不属于模块背景，也不计入任何模块的正文。未复制用户附件、聊天记录、个人配置或原始业务材料。

## 项目依据

- [仓库主分支](https://github.com/thus-zhou/Openthu)：本次读取基线 9135a75；运行代码、查询注册、事务执行及存储实现用于确认修改入口。
- [能力矩阵](https://github.com/thus-zhou/Openthu/blob/main/docs/CAPABILITIES.md)及[交接文档](https://github.com/thus-zhou/Openthu/blob/main/docs/HANDOVER.md)：用于区分已实现、历史实测、待验证和未实现能力。
- [已有诊断 PR #2](https://github.com/thus-zhou/Openthu/pull/2)：用于保留现有实现与测试，不能把尚未整体审查的贡献当成已发布新版本。
- [完整升级任务 #4](https://github.com/thus-zhou/Openthu/issues/4)及[批次交付约定](https://github.com/thus-zhou/Openthu/blob/main/docs/BATCH_UPGRADES.md)：一个版本计划、一个集成 PR、人工接力和 Codex 发行。
- 项目内 `vendor/madmodel-proxy/platform/linux/credentials.js`、`platform/credential-store.js`：已存在 Linux 密码原语与旧格式兼容；本次计划解决的是 Openthu 的完整接入、保护边界及迁移，不声称上游完全没有 Linux 实现。

## 权威技术来源

- [cryptography 稳定版 AEAD 文档](https://cryptography.io/en/stable/hazmat/primitives/aead/)：认证加密保护密文与附加数据，密钥必须保密，同一密钥不能重复 nonce。方案使用成熟接口，具体记录布局、权限检查和迁移属于 Openthu 的设计决定。
- [cryptography 官方发布元数据](https://pypi.org/pypi/cryptography/json)：规划时稳定版本为 50.0.2；执行前按冻结过程核对支持环境和文件完整性。
- [Pillow 官方 Image 文档](https://pillow.readthedocs.io/en/stable/reference/Image.html)及[官方发布元数据](https://pypi.org/pypi/Pillow/json)：为图像解码与资源限制提供依据；规划版本 13.0.0 要求 Python 3.11 以上，本计划统一采用 Python 3.12 起点。
- [RFC 5545](https://www.rfc-editor.org/rfc/rfc5545)：日历格式的标准依据。项目还需要自己实现稳定事件编号、来源精度与用户导出边界，不把时间戳列表当成已符合标准的日历。
- [GitHub 协作与维护分支说明](https://docs.github.com/en/pull-requests/how-tos/work-with-forks/allowing-changes-to-a-pull-request-branch-created-from-a-fork)：分支协作需要相应权限；本计划使用已有仓库权限，不向其他执行者分发个人令牌。

## 两份方案的合并结果

| 来源方向 | 最终落点 | 调整理由 |
|---|---|---|
| 首装诊断与运行体验 | 2.1、6.3 | 保留 PR #2 贡献，进一步解决独立安装和发行资源 |
| 统一核心与轻量本地界面 | 3.2、6.1、6.2、7.1 | 先冻结接口、后接线，本地看板限定只读业务 |
| 跨平台安全会话 | 2.2、3.1 | 不以机器属性替代秘密，也不搬迁本机凭据 |
| 完整学业数据 | 2.3、4.1、5.4 | 先来源与字段依据，课表、考试、成绩分别处理 |
| 图书馆体育闭环 | 4.3、4.4、5.1、5.2 | 保留已有适配，统一预检、授权和未知恢复 |
| 正式交作业与续借 | 2.3、5.1、5.3 | 上传也是副作用，资格与成功分别核对 |
| 模型图片和资料上下文 | 3.3、4.5 | 先素材隐私边界，再按已核对协议传输 |
| 课程资料中心 | 4.2 | 先做检索归档，不无条件扩大为 OCR 和知识库 |
| 增量事件和外部协同 | 5.4 | 提供可消费事件，不内置微信授权和后台守护 |
| 版本式整体交付 | 1.1、8.1、9.1 | 小步提交，整版本交审，Codex 审查后正式发布 |

Gemini 对 v0.1 的“只读预览”概括过窄：实际已有专用办理适配与事务机制，主要缺口是不同业务的证据、可靠性和完整平台接入。最终计划保留这些已有资产，不推倒重写，也不将旧框架文档中的阶段性描述当成当前注册事实。

所有工程上限、内部操作建议和新文件路径都是本方案的实现约定，不是学校规则或已存在的官方接口。学校真实接口、字段和业务条件必须由 2.3 的来源结论约束，执行者不能将本文转换为凭空存在的学校接口地址。
