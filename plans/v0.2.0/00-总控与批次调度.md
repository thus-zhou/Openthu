# Openthu v0.2.0 最终升级方案：总控与批次调度

日期：2026-11-16。状态：完整规划交付，尚未启动功能实施。本方案吸收现有项目盘点、此前简案和 Gemini 建议，以当前仓库实际代码为依据，组织为九批二十四个独立模块。每个模块只有一个方案文件，不附加长篇背景。

## 1. 升级目标与范围

本版要形成一个完整可交付的校园助手升级：首装诊断与配置、跨平台加密和会话、统一校园数据、课程资料中心、学业查询、日程增量和导出、模型图片输入、已有办理加固及受契约约束的新写适配、轻量本地看板、完整安装包和维护发布。

业务架构为：MCP / CLI / 本地只读看板 → 统一业务门面 → 查询与资料、日程、模型、事务引擎 → 校园服务适配器 → 认证网关与加密存储。来源证据与错误语义贯穿各层，不能绕过业务门面直接增加任意接口调用。

本地看板使用受控的 Python 轻量 HTTP 服务与本地静态 HTML/CSS/JavaScript；不新增外部 CDN 或统计服务，不默认绑定公网。Node 继续承担已有校园网关和协议逻辑，密码学实现集中到受控提供者，避免两端各自创造密文格式。

### 必须完成的产品底座

模块交付必须包含：诊断配置、真实平台加密后端、会话适配、完整性和隐私规则、资料中心、既有图书馆与体育能力加固、日程增量和导出、业务门面、本地读取看板、完整发行资源、回归和升级文档。原有工具与明确的旧参数继续兼容。

### 先满足来源契约的能力

个人课表、考试、成绩、正式交作业、图书馆续借、学校模型图片传输均有明确实施模块，但其生产实现依赖可靠来源。来源充分就按本计划完成，不得自行降为占位功能；来源不足则记录具体阻塞，不猜接口、不开假成功。它们属于本方案承诺范围，若无法完成，版本停在候选；缩减范围必须由使用者明确决定，不能由执行者悄悄调整。

本方案不安排现场演示、录屏、人工占座、真实付款或真实交作业来作为工程验收。采用自动化检查、合成传输、受控浏览器测试、契约证据、故障注入和安装恢复。代码与工程验证通过不提升真实校园业务的证据等级。正常来源研究也不得擅自上传个人响应或把凭据迁往云端。

## 3. 编号和批次屏障

编号的第一位表示批次，第二位表示该批中的模块。只有前一批全部模块完成、验收并回接到同一集成提交，下一批才能开工。第一批、第八批、第九批只有一个模块，是不可并行的串行关口；第二至第七批内可并行。可并行表示依赖与修改范围允许，资源不足时可以按编号依次完成。

## 4. 并行工作纪律

一个版本计划、一个集成分支、一个版本 PR。模块提交可以频繁，模块结束后继续下一项，不逐模块交审。辅助分支不是额外版本 PR；集成人顺序回接。Hermes 负责端到端开发和候选准备，Codex 负责整体审查、正式合并、标签、Release 与维护。

同批模块使用各自的工作区、虚拟环境、临时状态和端口，不共用一个可变安装目录执行 pip/npm，也不在别人运行时重装 node_modules。第一批冻结依赖提案后，各模块按同一组直接依赖开发；第六批统一形成平台锁文件。需要调整依赖时先记录影响，禁止同批执行者各装一个不兼容版本。

执行者不得撤销他人工作。公共入口、网关接线和包元数据由指定模块独占；其他模块给出接线请求，不自行改共享文件。产生跨范围冲突时暂停该修改，交给集成人安排，不能以“先改了再说”破坏并行条件。

## 5. 第一批必须冻结的工程决定

1. 开发与发行最低 Python 3.12，初始验证范围为 3.12/3.13，保持既有工具和命令接口；最低运行时提升必须写入升级说明，旧运行环境用户保留使用 v0.1 的路径。Node 基线为 24.18.0，初始 CI 为 Ubuntu 24.04 与 Windows 2025。
2. 直接依赖提案：cryptography 50.0.2、Pillow 13.0.0；既有 requests 2.33.0、Playwright 1.57.0、pytest 8.3.4、build 1.2.2.post1；Node tough-cookie 6.0.0 及现有传递锁作为起点。前两项在规划时已查证官方发布元数据。第一批仍需验证各目标环境 wheel 和许可证，实际变更必须同步记录；不使用开发预览版，不让每个模块自行选择 latest。
3. Linux 新存储采用随机秘密主密钥和认证加密，缺密钥拒绝相关生产存储；外部密钥文件与数据目录分离，限制所有者、权限和链接。Windows 继续保留旧 DPAPI 的正确读取，不自动把原有个人凭据导往云端。上游机器绑定兼容机制不能被误写成 Openthu 全部状态已安全跨平台。
4. 保留现有 29 个 MCP 工具入口。新查询和办理优先在统一入口登记，各操作的读写属性与授权保持明确。诊断、查询、导出和看板可以扩展 CLI，但原调用格式要继续可用。
5. 时间默认 Asia/Shanghai，日期级与精确时刻分别建模；来源失败不等于空，快照完成不等于来源完整，未知状态不能替换成成功。
6. 图片首版只接收经过本地检查的 JPEG/PNG/WebP，工程上限为单图 8 MiB、每次 4 图、总 16 MiB、单图 1600 万像素；平台契约若更严格则取较小值。大小与类型检查不能被压缩、编码或模型选择绕过。
7. 本地 API 只提供业务读取，默认回环监听；请求体上限 64 KiB、默认分页 50/上限 200、默认 UI 等待 30 秒、主动刷新最短间隔 10 秒，长内容通过分页返回。它们是工程限制而非学校规定，必须集中配置；原 MCP 超时语义保持兼容。
8. 新功能状态分别记录实现、运行环境与来源验证；素材、成绩、课表、事件和事务都按账号与用途隔离。只读看板不暴露写入、付款、密钥配置或自动模型生成接口。

## 6. 统一验收与范围决策

每模块至少交付：实现或明确阻塞、对应提交、契约、必要测试、安全结果摘要、回退办法和下一步。文档与纯规划不为凑数量编写镜像测试。批次回接运行必要联调及完整离线回归；第一批规划阶段可将代码基线检查作为前置，不能假装已经运行未来不存在的命令。

校验项目包括：旧接口兼容、两平台存储边界、真实生产代码与测试编码器隔离、来源完整性、取消和未决恢复、素材选择、浏览器和本地 API 安全、发行资源及隐私。原始日志不入公共仓库，报告只含脱敏摘要。执行具体校园写入始终需要针对该笔事项的授权，版本开发授权不代替业务授权。

条件适配有缺口时更新阻塞表并继续独立工作；若到第八批仍不能达到承诺范围，停在候选，交由使用者决定补证据、延期或明确缩减。禁止静默剔除难项、改口径、关闭失败测试或拿模拟响应冒充真实站点成功。

第九批只由 Codex 整体审查、合并和发行。独立审查通过并且公开下载校验成功，才标记 v0.2.0 正式完成；Hermes 不提前创建正式标签和 Release。
